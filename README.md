# line-recruitment-system20261006

## 概要

- LINE Messaging API を利用した採用応募受付システムのV2移行版です。
- 応募フロー：募集媒体 → 通常質問 → 事前確認事項 → 写真1枚提出 → 応募完了。応募に必要な写真は1枚のみです（顔写真・全身写真の2枚提出は廃止しました）。
- `userState:${userId}`（Script Properties）は「応募途中セッション」の一時データです。応募完了後は削除されず、個人情報を含まない最小限のDONEマーカー（`{ status, applicationNo, completedAt }`）に置き換わります。応募完了済みかどうかの恒久判定には使用しません。
- 完了済み応募の履歴は、Script Propertiesではなく「応募管理」スプレッドシートをSource of Truth（正）として管理します。
- **二重保存判定の最終的な拠り所（Source of Truth）は「応募管理」スプレッドシートです。** 応募保存処理は排他ロック内で、まず応募管理シート側に当該ユーザーの完了履歴が既にあるかを確認し、あればDONEマーカーの状態に関係なく保存をスキップします（DONEマーカーの保存自体に失敗していた場合でも、シート側の記録だけで二重保存を防げます）。DONEマーカーは、Webhook再送等への反応を早くするための補助的な冪等性ガードという位置づけです。
- 現在のV2仕様では、過去に応募完了したユーザーの再応募（2回目以降の応募保存）は許可していません。正式な「再応募機能」は今回のスコープ外で、将来別途設計します。

## セットアップ手順

- 応募No採番・応募管理シート保存の排他制御には `LockService.getScriptLock()` を使用しています。GAS標準機能のため、追加の設定・有効化作業は不要です。

### V2専用Apps Scriptプロジェクトの作成方針：standalone と container-bound（Spreadsheet-bound）のどちらが適切か

**結論：V2は container-bound（特定のV2テスト用スプレッドシートに紐づいたコンテナバインドスクリプト）を強く推奨します。standalone（非バインド）スクリプトは推奨しません。**

理由：

- このコードベースは `SpreadsheetApp.getActiveSpreadsheet()` に強く依存しています（例：`10_CommonUtils.gs` の `getConfigValue_()`、`12_ApplicationSheet.gs` の `saveApplicationFromState_()` など、設定読み込み・応募保存・ログ書き込みなど主要処理のほぼすべてで使用）。
- `getActiveSpreadsheet()` は、スクリプトが特定のスプレッドシートに「コンテナバインド」されている場合に、そのスプレッドシートを正しく返します。standalone スクリプトとして単体で作成し、Webhook（`doPost`）経由で実行した場合、「アクティブなスプレッドシート」という文脈自体が存在しないため、`getActiveSpreadsheet()` は正しく動作しません（nullが返る、またはエラーになります）。
- 本番環境も、同様の理由から container-bound 構成になっていると考えられます（コードの作り自体がそれを前提としているため）。
- したがって、V2テスト用スプレッドシートを新規作成した上で、そのスプレッドシートの「拡張機能 → Apps Script」からApps Scriptプロジェクトを開く形（＝そのスプレッドシートにバインドされた新規スクリプトプロジェクト）で作成してください。これにより新しいV2専用のscriptIdが発行されます。

### `.clasp.json` の扱い

- `.clasp.json` は、ローカルのGitリポジトリ直下に各自が作成するファイルで、`scriptId`（および`rootDir`等）を保持します。例（値はダミーです。実際の値は入力しないでください）：
  ```json
  {
    "scriptId": "<V2専用のscriptId>",
    "rootDir": "."
  }
  ```
- **`.clasp.json` はこのリポジトリの `.gitignore` に登録済みで、Gitの追跡対象外です。** コミット・pushには含まれません。
- `scriptId` は必ず、上記で新規作成したV2専用のものを使用してください。**本番のscriptIdを絶対に入力しないでください。**
- このラウンドでは `.clasp.json` ファイル自体の作成も行っていません（clasp認証・プロジェクト作成を伴わないため）。`.clasp.json` の作成は、ユーザーがV2用Apps Scriptプロジェクトを作成した後、ご自身の端末で行ってください。

## 環境変数 / スクリプトプロパティ

- `userState:${userId}`：応募途中ユーザーの一時的なセッションデータです。応募管理シートへの保存成功後、自動的に以下の最小限のDONEマーカーに置き換わります（削除はしません）。
  ```
  { "status": "完了", "applicationNo": <応募No>, "completedAt": "<ISO日時>" }
  ```
  DONEマーカーには氏名・年齢・電話番号・店舗回答・質問回答・備考・写真状態などの個人情報は一切含まれません。Webhook再送等による同一応募の二重保存を防ぐための補助的・短期的な冪等性ガードであり、応募完了済みかどうかの恒久判定には使用しません（恒久判定も、二重保存の最終判定も「応募管理」シートで行います。DONEマーカーの保存自体に失敗していても、シート側の判定だけで二重保存を防げます）。
- 秘密情報（LINEチャネルアクセストークン等）はScript Propertiesではなく、本番と同様にスプレッドシートの「設定」シートで管理します。実値はこのREADMEには記載しません。

### V2テスト環境向けのScript Properties

- 本番の `userState:*`（応募途中セッション・DONEマーカー）、および `MTG_TRIGGER_VER` は、**V2テスト環境へは移行しません。** V2テスト環境は、応募状態に関して空の状態（Script Propertiesに何も入っていない状態）から開始します。

## Spreadsheetの構成方針（2026/10改訂：説明行統一）

通常の管理・マスタ・ログシートは原則として、

1行目：最新V2ヘッダー
2行目：各列の説明
3行目以降：実データ

として管理する。

設定シートなど、行そのものが設定値やドキュメントを構成する特殊シートはこの限りではない。

setupRecruitSpreadsheet() は既存データを保持しながら、
ヘッダーおよび説明行を最新V2仕様へ更新する。

既存の2行目が実データの場合はデータを保護したうえで説明行を挿入する。
すでに説明行が存在する場合は重複挿入せず内容のみ更新する。

**背景：** 以前のラウンドでは「旧データ領域」と「V2データ領域」をシート内で物理的に分離する「V2ヘッダー追記方式」（`findLatestHeaderRow_` / `resolveV2HeaderRow_` / `ensureV2HeaderBlock_` によるヘッダー完全一致スキャン）を採用していましたが複雑すぎたため廃止し、続く改訂で一旦「1行目＝ヘッダー／2行目以降＝データ」というシンプルな構成に統一しました。今回の改訂では、応募管理・対応管理が元々持っていた「2行目＝説明行」という構成を、質問設定・選択肢設定・連絡先・対応履歴・ユーザー管理・エラーログ・処理ログにも広げ、通常の表形式シート全体で「1行目＝ヘッダー／2行目＝説明／3行目以降＝データ」に統一しています。

### 基本方針

1. **既存シートは削除しません。既存データ行も削除しません。**
2. **1行目は、setupを実行するたびに最新のヘッダー定義で無条件に上書きします。**
3. **2行目（説明行）は共通ヘルパー `ensureDescriptionRow_()`（`10_CommonUtils.gs`）で安全に保証します。** 2行目が既に実データである場合は、2行目の手前へ新しい行を挿入してからデータを3行目以降へ押し下げ、その上で2行目に説明文を書き込みます（既存データは一切失われません）。2行目が既に説明行（または空白）の場合は、行を増やさずその場で説明文を最新内容へ上書きするだけです。判定に迷うケースは必ず「データ」側として扱い、行を挿入します。
4. **3行目以降の既存データ行は、setupを何度実行しても一切変更しません。**
5. **列を削除した場合、その列を物理的に持っていた旧データ行は、削除後の新しい列構成とは意味がズレて表示されることがあります。** これは明示的に許容されたトレードオフです（旧データ行自体を削除することはしません）。
6. **入力規則（ドロップダウン等）・条件付き書式・日付書式などのデータ用書式は、原則としてデータ領域（3行目以降）にのみ適用します。** 説明行（2行目）にはデータ用の入力規則・プルダウン・チェックボックスは一切設定しません（背景色・文字色・折り返しなど説明用の書式のみ設定します）。

### 既知の不具合と対処（2026/10・説明行の入力規則残留）

質問設定シートで、2行目へ最新説明文を書き込もうとした際に「入力規則に違反しています（文字入力, 選択ボタン のいずれかの値を入力してください）」というエラーで `setupRecruitSpreadsheet()` が失敗する不具合がありました。原因は、2行目がまだデータ行だった旧バージョンの名残で、E2セルに「文字入力／選択ボタン」のドロップダウン入力規則が物理的に残ったままになっており、そこへ複数値をまとめた説明文（例："選択ボタン / 文字入力"）を書き込もうとして規則違反になったことです。

この対処として、`ensureDescriptionRow_()` は2行目へ説明文を書き込む直前に、必ずその2行目に対して `clearDataValidations()` を呼び出すようにしました（`setValues()` の前に `clearDataValidations()` を実行）。これは入力規則のみを解除し、背景色・文字色・折り返しなどの書式は変更しません。応募管理・対応管理（`ensureDescriptionRow_()` を経由せず直接notes行を書き込む2シート）についても、notes書き込み直前に同様の `clearDataValidations()` を追加しています。これにより、2行目にどのような旧入力規則が残っていても、setupは常にエラーなく完了します。

### 応募管理・対応管理（1行目＝ヘッダー／2行目＝説明行／3行目以降＝データ）

応募管理・対応管理は、今回の改訂以前から「1行目＝ヘッダー、2行目＝説明行、3行目以降＝実データ」という構成でした。以下の複数の処理がこの3行目開始を前提に実装されており、変更すると冪等性・重複防止ロジックが壊れるため、今回もこの2シートはデータ開始行を固定で3行目のままとしています。

- 応募No採番（`12_ApplicationSheet.gs` の `generateApplicationNo_`）
- 重複保存防止・Source of Truth判定（`hasCompletedApplication_` / `countCompletedApplicationsByUserId_`）
- LockServiceによる排他制御と組み合わせた保存処理全体（`saveApplicationFromState_`）
- 対応管理との同期処理（`13_SupportSheetSync.gs`）、対応履歴への反映（`14_SupportHistory.gs`）
- 対応管理の条件付き書式（`setupSupportStatusConditionalFormat()`）
- 管理者通知・応募行検索（`8_AdminNotify.gs`、`2_Menu.gs` の件数表示など）

### 連絡先シートの変更点

連絡先シートは、前回の改訂で一度「1行目＝ヘッダー、2行目以降＝データ」に簡素化しましたが、今回の改訂で再び「1行目＝ヘッダー、2行目＝説明行、3行目以降＝データ」へ戻しました。`ensureContactHeader_()`（`15_Contacts.gs`）は友だち追加・メッセージ受信のたびに毎回呼ばれますが、1行目は最新ヘッダーと一致していれば書き込みをスキップし、2行目の説明行は `ensureDescriptionRow_()` が既存データを保護しながら安全に管理するため、既存データへの影響はありません。検索・走査（`findContactRowByUserId_` など）・追客送信（`19_ContactMessage.gs`）は、いずれも3行目以降のみを対象とするよう修正済みです。

### 設定シートの値保護

設定シート（`SHEET_CONFIG`）は特殊構造シートであり、今回の説明行統一の対象外です（行そのものが「キー／値／説明／備考」という設定値を構成しているため）。setupを再実行しても、既に入力済みの値（特に `LINE_CHANNEL_ACCESS_TOKEN` と `ADMIN_GROUP_ID`）を上書き・リセットしません。既存の値が空欄のキーのみ、デフォルト値／プレースホルダー文言で補完されます（詳細は `11_SetupSpreadsheet.gs` の `setupConfigSheetForRecruit_` を参照）。秘密情報の実値は、コード・README のいずれにも記載していません。

### ユーザー管理シートについて

ユーザー管理シートは、Script Propertiesの現在のライブセッション状態を同期のたびに全行再生成する「使い捨てのミラー」（過去ログではない）であるため、3行目以降のデータ全体書き換えは引き続き許容されます。今回の改訂では、この全行再生成（`syncUserStatesToSheet()`）を挟んでも2行目の説明行が失われないよう、`ensureUserManagementHeader_()` が毎回 `ensureDescriptionRow_()` で説明行を保証するようにしました。データ書き込み開始行も2行目から3行目へ変更しています。

### 1枚写真フローに伴う列削除

旧2枚写真フロー（顔写真・全身写真の2枚提出）を前提にしていた以下の列を削除しました。

- 応募管理シートの「全体写真確認」列
- ユーザー管理シートの「全身写真状態」列

これらの列を物理的に持っていた旧バージョンのデータ行は、削除後の新しい列構成とは列の意味がズレて表示される場合がありますが、上記「基本方針」のとおり許容されるトレードオフです。引き続き使用する列は、応募管理の「写真受信数」「顔写真確認」、ユーザー管理の「写真受信数」「顔写真状態」です。

### `20_MTGSummary.gs` について

このファイルは「シートの先頭6行だけをスキャンしてヘッダーらしき行（列名が一致する行）を自動検出する」仕組み（`findSheet_`）を使っています。ヘッダー行自体は検出ロジック上、列名そのもので判定されるため説明行と混同されることはありません。ただし検出したヘッダー行の直後（`headerRow + 1`）からデータとして読み込むため、2行目が説明行であるシート（応募管理・対応履歴）では、説明行が1行だけ余分に読み込み対象へ含まれます。実際の集計処理を確認したところ、応募管理側は説明行のNo列（"自動採番"）が数値実績として参照されることはなく、対応履歴側は種別（`種別`列）の完全一致判定（面接入力／体入入力／本入入力のみ）により説明行は自動的に除外されるため、集計結果への実害はないことを確認済みです。大規模な改修は行わず、現状のままとしています。

## 運用手順

- 応募フローは、募集媒体 → 通常質問 → 事前確認事項（「事前に伝えておきたいことや、確認しておきたいことがあれば教えてください！特になければ「なし」と送ってください。」）→ 写真1枚提出 → 応募完了、の順です。写真は1枚のみで、2枚目は要求しません。
- 応募完了後は「応募管理」シートに応募履歴が残ります。担当者は応募履歴の確認にはこのシートを使用してください。
- 過去に応募完了したユーザーが「応募開始ワード」を送信した場合、または再度友だち追加（followイベント）した場合のいずれであっても、新しい応募フローは開始されません（応募管理シートの履歴をもとに判定します）。通常の新規ユーザーのfollowイベントは、従来通り応募フローが自動開始されます。

## トラブルシューティング

- LINEへの完了reply（返信）が失敗した場合でも、応募データの保存自体は成功している可能性があります。ユーザーから「返信が来ない」等の問い合わせがあった場合は、まず「応募管理」シートに該当ユーザーの応募が保存されているか、および処理ログ・エラーログを確認してください。
- エラーログに `APPLICATION_DUPLICATE_SAVE_SKIPPED` が記録されている場合は、Webhookの再送等により同一応募の保存処理が複数回実行され、2回目以降が重複保存として正しくスキップされたことを示します。異常な不具合ではありませんが、頻発する場合はLINE側の配信状況（応答遅延など）を確認してください。
- エラーログに `APPLICATION_SAVE_SKIPPED_NO_STATE` が記録されている場合は、保存処理の実行時点で該当ユーザーの`userState`が存在しなかったことを示します（応募途中でない状態での画像受信など）。
- 「写真を送ったのに応募が完了しない」：該当ユーザーの`userState`（Script Properties）を確認し、ステータスが応募途中の値（写真提出待ち等）のままになっていないか、処理ログ・エラーログに保存失敗の記録がないかを確認してください。
- 「DONEマーカーが残っている」：応募完了後、`userState:${userId}`には削除ではなく`{status:"完了", applicationNo, completedAt}`の形のDONEマーカーが残り続けるのが正常な挙動です（個人情報は含まれません）。消えないこと自体は異常ではありません。
- 「LINEの完了メッセージが届かない」：処理ログに`APPLICATION_SAVED`が記録されていれば保存自体は成功しています。reply失敗時はエラーログに`COMPLETE_REPLY_FAILED_AFTER_SAVE`が記録されるため、その有無を確認してください。
- 「二重応募が疑われる」：「応募管理」シートに同一ユーザーIDの行が複数あるか確認してください。保存処理は応募管理シート側に完了履歴が既にあれば必ず保存をスキップするため、通常は複数行になりません。Webhook再送等による重複保存の試行は、エラーログの`APPLICATION_DUPLICATE_SAVE_SKIPPED`で正しくスキップされたことを確認できます（メッセージ内容で「応募管理シートの履歴による判定」か「DONEマーカーによる判定」かを区別できます）。
- 「写真関連の列について」：写真提出は1枚のみのため、「応募管理」シートの「全体写真確認」列、「ユーザー管理」シートの「全身写真状態」列は、2026/10のスキーマ簡素化で列自体を削除しました。これらの列を物理的に持っていた旧バージョンのデータ行は、列構成のズレにより表示内容が本来の意味とずれて見える場合がありますが、異常ではありません（旧データ行自体は削除していません）。実際に使われるのは「顔写真確認」（応募管理）・「顔写真状態」（ユーザー管理）・「写真受信数」です。対応管理・対応履歴・管理者通知はいずれも写真関連の列に依存していません。
- 備考：`APPLICATION_DUPLICATE_SAVE_SKIPPED` / `APPLICATION_SAVE_SKIPPED_NO_STATE` / `COMPLETE_REPLY_FAILED_AFTER_SAVE` は、処理ログの記録種別を制限する `PROCESS_LOG_ALLOWED_TYPES`（1_Config.gs）に含まれていないため、あえて「エラーログ」シート側に記録しています（1_Config.gsは今回の変更対象外のため許可リストへは追加していません）。
